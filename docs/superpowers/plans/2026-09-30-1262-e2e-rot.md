# E2E rot: the rot check's stack runs with tracing off (#1262) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Base:** origin/develop at **0d9b14c80**. The failing run tested bf742411e. Between the two SHAs, none of the files this plan reads or edits changed except `docs/local-docker.md`, and its §10 anchor is quoted from 0d9b14c80.

**Goal:** Close #1262. Both failing Playwright tests (`e2e/onboarding.spec.ts:201` and `:242`) fail because the whole stack became slow, not because the spec or the app is wrong. Since #983 (2026-09-11), the dev `php` container traces every request and every DBAL query with OpenTelemetry (`always_on`). The rot workflow boots that container unchanged, so the backend now runs about 3.5x slower there. A real onboarding journey (register, confirm, sign in, subscribe) no longer fits in Playwright's 30 s test timeout. The fix: the rot workflow boots `php` with both tracing gates off, the same lever `composer test` and the Infection scripts already use. `docker-compose.yml` reads the two gates from the environment, following `docker-compose.prod.yml`'s pattern, and developers keep tracing on by default.

**Architecture:** No app code changes and no spec changes. Two config lines per service in `docker-compose.yml`, one job-level `env:` in `.github/workflows/e2e-rot-check.yml`, and one paragraph in `docs/local-docker.md` §10. The first task measures locally before anything is committed. If the measurement does not confirm the tax, the executor stops and reports.

**Tech Stack:** Docker Compose v2 variable interpolation, GitHub Actions job `env:`, OpenTelemetry PHP (`OTEL_PHP_AUTOLOAD_ENABLED`, `OTEL_PHP_DISABLED_INSTRUMENTATIONS`), Playwright 1.61, PHPUnit black-box e2e (`composer e2e`).

**Branch:** `fix/1262-e2e-rot` off `develop`. It is not `test/…`, because the change is to the stack config and not to specs. One PR, body ends `Closes #1262`.

### Cause: #983's always-on tracing in the container the rot workflow boots

The observability work sits exactly between the fast run (df2439088, 09-08) and the first slow one (1a35d917e, 09-16): `912e78805` 2026-09-11 "add OpenTelemetry SDK and Symfony auto-instrumentation", `d2e5575ac` 2026-09-11 "install the OTel extension", `f53e63aee` 2026-09-13 "trace every DBAL query as a span with its SQL text", `152958c43` 2026-09-13 "open a span on the entry-point methods of the hot API routes". Nothing in `frontend/src/app/discover`, `Service/Catalog` or `Service/Subscription` changed between the passing 09-23 run and the failing 09-24 run. The only candidates in that window are `ce5b6cf53`, `ecced880f` and `83c76d546`, and none of them is on the subscribe path.

- `docker-compose.yml:63` `OTEL_PHP_AUTOLOAD_ENABLED: "true"` and `:70` `OTEL_TRACES_SAMPLER: "always_on"` on `php`, with no way to override either from outside.
- `.github/workflows/e2e-rot-check.yml:136` `run: docker compose up -d --wait mysql mailpit php nginx frontend`. This boots that `php` container as it is, without `tempo`, so every export also targets a host that is not running.
- The repo already knows about this tax. CLAUDE.md says the dev stack "exports OpenTelemetry traces on every query, and a bare phpunit inherits that env — a ~6x tax". `backend/composer.json:135-137` `"test": ["@putenv OTEL_PHP_DISABLED_INSTRUMENTATIONS=all", "@php bin/phpunit"]` (`15b12d820`, 2026-09-13). The e2e stack never got the same switch.
- `docker-compose.prod.yml:70-74` documents the lever: "Both vars gate tracing together -- AUTOLOAD_ENABLED alone does not." `OTEL_PHP_AUTOLOAD_ENABLED: ${OTEL_PHP_AUTOLOAD_ENABLED-false}` / `OTEL_PHP_DISABLED_INSTRUMENTATIONS: ${OTEL_PHP_DISABLED_INSTRUMENTATIONS-all}`, and an empty `DISABLED_INSTRUMENTATIONS` means "nothing disabled".

### Ruled: spec rot or app regression?

Neither. It is an **environment regression in the e2e stack**. The spec's assertions still describe the app correctly: 09-03 to 09-09 passed in ~6 s, and 09-23 passed on the slow stack. The app's onboarding code did not change in the failing window. Task 1 confirms the cause locally before any commit.

## Decisions

- **D1: fix the stack, not the spec's budgets.** Raising the onboarding test's timeout (`test.slow()`, or `test.describe.configure({ timeout })`) would make both tests pass while leaving a 3.5x slower stack under every spec. The next victim (`settings-admin-smoke.spec.ts:165` at 25.2 s) would follow, and the rot check exists to catch exactly this kind of slowdown. #1061 (`d88c5846b`) already widened the step budgets for the same cause, read then as "CI cold-start load". Those budgets stay: they are harmless once the stack is fast. The spec is not edited.
- **D2: switch tracing off with the two gates prod already uses** (`OTEL_PHP_AUTOLOAD_ENABLED=false` plus `OTEL_PHP_DISABLED_INSTRUMENTATIONS=all`), read from the environment in `docker-compose.yml` with dev defaults `true`/empty. Developers keep tracing on by default. The rot workflow sets both at **job** level, so every compose call in the job sees them and no later step can recreate `php` with tracing on. `worker` gets the same interpolation, because its env block duplicates `php`'s and a developer switching tracing off wants both. The rot workflow never boots `worker`.
- **D3: not booting `tempo` in CI instead.** That would keep the tax. The measured ~6x is instrumentation plus export, not only failed exports.
- **D4: Loki and Pyroscope stay as they are.** Pyroscope profiling is off by default (admin toggle). Loki pushes at `kernel.terminate`, after the response. Task 1 names Loki as the next suspect if switching tracing off does not bring the time back.
- **D5: 44e23741b ("Offer suggested feeds only to accounts with few subscriptions", 2026-09-27) is not the cause of `:242`.** `suggestFeeds` (`entry-list.component.ts:510-514`) adds `this.subscriptions.resolved()`. That signal is already true after the skip: the onboarding redirect only fires on a resolved store (`reader-shell.component.ts:706`), and `SubscriptionsStore.loadIfStale()` does not reload inside the 30 s freshness window (`sidebar-freshness.ts` `SIDEBAR_RELOAD_INTERVAL_MS = 30_000`), so `resolved` is never taken back down. Task 4 checks this: if `:242` still fails at the link on a fast stack, the executor stops and reports with the error-context snapshot.
- **D6: no automated guard for the workflow env.** No test can run a workflow's env. The rot run itself is the guard: Task 5 dispatches it once on the branch before merging, and a red run blocks the merge.
