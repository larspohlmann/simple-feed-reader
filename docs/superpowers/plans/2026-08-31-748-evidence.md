## The five open questions

### 1. NPR — where does the mp3 URL live?

**Both.** The mp3 URL appears in an anchor `href` attribute AND in a `<script>`
JSON block.

- Attribute: `<a class="audio-module-listen" href="https://ondemand.npr.org/anon.npr-mp3/npr/wesun/2026/08/…dark_energy.mp3?t=progseg&…">`, and a second `<a>` under `audio-tool-download`.
- Script JSON: the same URL with escaped slashes (`ondemand.npr.org\/anon.npr-mp3\/…`), so it is present inside a `<script>` payload too.

The bare path returns the audio; the query (`t=progseg`, `e=`, `sc=siteplayer`,
`aw_0_1st.playerid`) is player telemetry, not a signature. `NprAudio` may read
either location — the attribute is the simpler, script-strip-proof choice.

**Decision: NprAudio ships.**

### 2. heise — the contradiction resolved

**Mechanism A is FALSE. There are zero real `<iframe>` elements on the page.**
The inline player is a proprietary custom element:

```html
<figure class="video video--fullwidth a-u-inline">
  <div class="video__yt-container">
    <a-iframe class="video__iframe" needs-consent name="Youtube"
              src="//www.youtube-nocookie.com/embed/M1j_uRqKMKI"
              title="YouTube video player" allowfullscreen>
```

The captured bytes are the real article ("lokale KI" appears 60 times, no consent
wall dominates the page). A separate `<a-video type="targetvideo">` element also
exists; it is heise's own "targetvideo" playlist widget (`entry-id="27360"`), NOT
the YouTube player, and it carries no YouTube id. The earlier comment was right
that the player is a proprietary element and wrong about the tag name: the
YouTube player is `<a-iframe name="Youtube">`, not `<a-video>`.

**Is `M1j_uRqKMKI` the article's own companion? YES.** Two independent signals:

1. The `<a-iframe name="Youtube" src="//…/embed/M1j_uRqKMKI">` sits inside the
   article's own `<figure class="video video--fullwidth">`.
2. The page's JSON-LD attaches it as a part of the article:
   `"hasPart":[{"@type":"VideoObject","contentUrl":"https://www.youtube.com/watch?v=M1j_uRqKMKI","identifier":"M1j_uRqKMKI","name":"YouTube-Video"…}]`, hung off the article's own URL node.

The other YouTube references on the page are channel/nav links
(`youtube.com/@ct3003`, `youtube.com/heiseonline`, `youtube.com/channel/UC1t9…`)
and are NOT this video.

**heise is IN SCOPE — the video is the article's own.** But the recovery
mechanism the plan assumes does not exist. See the "heise mechanism gap" warning
below; it gates Tasks 4 and 6.

### 3. ARD — are the MP4 renditions inside a `<script>`?

**No — the plan's stated mechanism is wrong, but the conclusion (read the raw
source) still holds.** The progressive MP4 rendition ladder lives in an
HTML-entity-encoded JSON blob inside a **`data-v` attribute** of
`<div class="v-instance preloadingskeleton--mediaplayer--16x9">`, not inside any
`<script>` element. Verified: `maxHResolutionPx` appears only inside that
`data-v` attribute (`&quot;maxHResolutionPx&quot;`), never inside a `<script>…</script>`.

The full ladder is present:
`tagesschau-progressive.ard-mcdn.de/video/2026/0831/TV-20260831-1025-3900.{webs,webm,webl,webxl,webxxl}.h264.mp4`,
highest labelled rendition `webxxl` at `maxHResolutionPx: 1920`. Poster from
`<meta property="og:image">` (a real `.jpg`). The `og:video` is only the
`~player.html` page, `type=text/html`, not a media file.

**Consequence for D1.** D1 justifies the raw-source scanner by "the normalizer
strips every `<script>`". For ARD that reason is inaccurate — the renditions are
in an attribute, not a script. The correct reason ARD needs the raw source: the
renditions sit in a custom-element `data-v` attribute that readability discards
and `EntrySanitizer` strips (it removes `class`, `data-*`), so nothing downstream
of the raw page ever sees them. `ArdVideo` must parse the JSON out of the
`data-v` attribute of `div.v-instance`, not out of a `<script>`.

**Decision: ArdVideo ships.**

### 4. Deutschlandradio — is the first `data-audio-src` this article's file?

**Not literally the first — the first four `data-audio-src` values are the live
stream, which the rule already rejects.** After the stream, the first on-demand

- Live stream (rejected): `https://st02.sslstream.dlf.de/dlf/02/128/mp3/stream.mp3` (×4).

The `st0N.sslstream.dlf.de/…/stream.mp3` rejection is load-bearing, exactly as
spec'd. The "first `data-audio-src`" wording in the rule must mean "first
on-demand `*.dradio.de` file after rejecting the live stream", not the literal

**Decision: DeutschlandradioAudio ships.**

### 5. Vimeo, Bandcamp, Spotify, Mixcloud — is there a real embedding article?

**No, for all four.** The embed-URL patterns return an empty result set against

content_html LIKE '%bandcamp.com/EmbeddedPlayer%' → 0 rows
content_html LIKE '%open.spotify.com/embed%'  → 0 rows

`<a href="https://dreamchimney.bandcamp.com/album/side-order">`,
`<a href="https://open.spotify.com/show/…">Spotify</a>`,
`<a href="https://vimeo.com/zivadynamics">Ziva Dynamics</a>`. Mixcloud does not
appear at all.

Per D8, a provider with no captured page does not ship. **All four drop.**

## heise mechanism gap — MUST read before Tasks 4 and 6

heise is in scope (the video is the article's own companion), but **no
source the plan currently specifies will reach it**:

- `InBodyEmbedRewriter` keys on a real in-body `<iframe>`. The page has none.
- `PageEmbedSource` scans the raw page for real `<iframe>` elements whose `src` a
  provider accepts. The heise player is a custom `<a-iframe>` element inside a
  `<noscript>`, not an `<iframe>`, so this scan skips it as written.

To recover heise, Task 6 must extend `PageEmbedSource` (or add a heise source) to
read the YouTube id from one of:

- the `<a-iframe name="Youtube" src="//www.youtube-nocookie.com/embed/{id}">` custom element, or
- the JSON-LD `hasPart` `VideoObject` `contentUrl`.

Either yields `M1j_uRqKMKI`, which the YouTube provider then normalizes. This is a
plan decision, flagged here, not resolved in Task 3. If Tasks 4/6 choose not to
handle the custom element or JSON-LD, heise silently recovers nothing despite
being "in scope", and that should be stated rather than left as a latent gap.

## Correction to spec D1 (record it in Task 4)

D1 attributes the need for a raw-source scanner to `<script>` stripping. For ARD
the renditions are in a `data-v` **attribute**, not a `<script>`. The scanner is
still correct; the reason is attribute/`data-*` stripping by readability and
`EntrySanitizer`, not script stripping. Deutschlandradio (`data-audio-src`
attribute) and heise (`<a-iframe>` custom element) confirm the same shape: the
durable media reference is in attributes and custom elements that survive only in
the raw source. NPR is the one case whose reference also survives as a plain
`<a href>`.
