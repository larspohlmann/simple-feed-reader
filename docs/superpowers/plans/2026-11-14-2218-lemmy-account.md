# Lemmy account: votes and replies — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect a Lemmy account in Settings, then upvote / downvote Lemmy posts and comments and reply to both from the reader, seeing one's own vote wherever the #2217 vote pill shows.

**Architecture:** `SocialNetwork::Lemmy` joins the enum as an *account-only* network: `carriesFeeds()` / `feedNetworks()` keep it out of everything feed-shaped (private feeds, the sync sweep, import, search, network pickers). A login exchanges the password for a JWT once; only the JWT is sealed. `LemmyPosts` finds a post or comment on the account's home instance, `LemmyVoting` casts votes there, and `DiscussionVotes` keeps the reader's post vote in a new `discussion_vote` table that the entry list reads as `myVote`. With an account, `LemmyCommentsSource` reads the thread from the home instance through a Comments-owned `LemmyThreadReaderInterface` (implemented in Social/Social), so each comment carries a `vote`. Replies reuse the composer endpoints through a Lemmy `PostResolver`, `ComposerDefaults` and `PostWriter`. In the SPA the vote pill's arrows become buttons; entry votes patch `EntriesStore` optimistically, comment votes go through `OptimisticToggles`.

**Tech Stack:** Symfony 8.1 / PHP 8.5 / Doctrine (SQLite + MySQL), Lemmy API v3 (0.19), Angular 20 standalone + signals, Transloco, Jest.

**Spec:** `docs/superpowers/specs/2026-11-14-2218-lemmy-account-design.md`

## Plan notes vs design

1. **Module boundary wording.** Content/Comments already imports `Service/Social/Bluesky` (`JsonNodeModel` in `LemmyThread`, `LemmyCommentsSource`, `SubstackThread`); Social/Bluesky is its own module. The edge that would close a cycle is Comments → **Social/Social** (Social/Social → Comments exists: `SocialRepliesSource`, `SocialResponses`, `SocialCommentLikes`). The plan keeps the Comments-owned `LemmyThreadReaderInterface`, implemented in Social/Social, and imports nothing from Social/Social into Comments.
2. **Post resolution is not "resolve the page URL, always".** A feed instance's post page is often a federated *copy*: `curl -H 'Accept: application/activity+json' https://lemmy.world/post/54394608` answers `308` to `https://crust.piefed.social/…`, and Lemmy verifies a fetched object's id against the URL it dereferenced, so `resolve_object` of a copy's page URL is not dependable; anonymously it answers `{"error":"couldnt_find_object"}` (checked on lemmy.world). The plan resolves the **origin `ap_id`** instead: when the post's host is the account's host, the page's id *is* the local id (`GET /api/v3/post?id=`); otherwise one anonymous `GET {feed instance}/api/v3/post?id=` yields `post_view.post.ap_id`, which `resolve_object` resolves on the home instance. Comments resolve their `ap_id` as designed. Cost: the ruling's "no special case for same-instance targets" is replaced by a same-host shortcut; cross-instance targets cost two calls before the action instead of one.
3. **Reconnect body.** The existing `PUT /api/me/social-accounts/{id}/credential` keeps `{secret}` and gains `totpToken?`; for Lemmy `secret` is the password and the username is the account's own name (from its identity). The instance URL is not resent: an account's instance is fixed.
4. **What gets sealed.** `SocialAccountConnector` seals `$credentials->secret` today, which for Lemmy would be the password. `VerifiedAccountModel` gains `credential` — what the verifier says to keep (the typed secret on Bluesky/Mastodon, the JWT on Lemmy) — and the factory and reconnect seal that. `SocialCredentialsModel::hint()` is `''` for Lemmy, so no character of the password reaches the `credential_hint` column.
5. **Optimism.** Entry votes patch `EntriesStore` through its existing `optimistic()` (as `setLiked` does), because list rows, cards and the article header all read the store; `OptimisticToggles` serves comment votes, with `to: true` meaning "the new vote shown" and `false` "the previous one restored".
6. **Stale votes after a fallback.** When the home instance cannot give the thread, the anonymous thread is served and cached under the account's scope; until that cache entry ages out, its comments show `myVote: 0`. The design is silent; the plan accepts this (a vote still resolves by `ap_id` and works).
7. **Feed-shaped leaks the design does not list** (its "left to the builder"): the connector's Home creation, `findIdsDueForSync`, the import and search endpoints (which take an account id), the `{network}` routes of network exclusions and saved-search inclusions, the link composer, and the backup restore of network lists. Task 2 closes each.
8. **Flagged, not planned:** disconnect does not sign the JWT out (`POST /api/v3/user/logout`); the session stays valid on the instance until the user revokes it there. `docs/security.md` says so (Task 10).

## Global Constraints

- Lemmy API v3 only (`/api/v3/…`), JSON bodies, `Authorization: Bearer <jwt>`; the JWT is sent only to the account's `serviceUrl`, never to a feed instance.
- Enum: `SocialNetwork::Lemmy = 'lemmy'`, `displayName()` `Lemmy`, `carriesFeeds()` false; `feedNetworks()` = `[Bluesky, Mastodon]`; `FEED_NETWORK_REQUIREMENT = 'bluesky|mastodon'`.
- Vote values `1 | 0 | -1` (`App\Enum\VoteScore`: `Up = 1`, `None = 0`, `Down = -1`); `discussion_vote` stores `Up`/`Down` only — no row is no vote.
- Endpoints: `POST /api/me/social-accounts/lemmy` `{instanceUrl, username, password, totpToken?}` → 201; `PUT /api/me/social-accounts/{id}/credential` `{secret, totpToken?}`; `PUT /api/entries/{id}/vote` `{score}` → `{myVote, score}`; `GET /api/entries/{id}/vote` → `{myVote}`; `PUT /api/entries/{id}/comments/vote?address=` `{score}` → `{myVote, score}`; replies through `GET …/social/composer` and `POST …/social/replies?address=`.
- Limits: connect/reconnect `social_account`; votes `social_like`; `GET …/vote` and the composer `social_viewer`; replies `social_writes`. No new limiter.
- Problems: only existing types (`social_credentials_rejected`, `social_account_missing`, `social_account_needs_reconnect`, `social_post_refused` 409, `social_post_not_found`, `social_post_unsupported`, `social_network_throttled`, `social_network_unreachable`). No new problem arm.
- Table `discussion_vote`: `id`, `user_id`, `entry_id`, `social_account_id` (FKs `ON DELETE CASCADE`), `score SMALLINT`, `voted_at DATETIME`; unique `(user_id, entry_id)`; indexes on `entry_id`, `social_account_id`. Dropped from backups wholly.
- Entry JSON `myVote: 1 | 0 | -1 | null` (null: no Lemmy post, or no Lemmy account in any status). Comment JSON `vote: {address, myVote, canReply} | null`.
- Lemmy comment body limit 10 000 characters (code points), Markdown sent as typed; no quotes, link posts or deletes on Lemmy (`social_post_refused`).
- Frontend: `SOCIAL_NETWORKS` stays `['bluesky', 'mastodon']`; `ACCOUNT_NETWORKS = ['bluesky', 'mastodon', 'lemmy']`. Icons: `arrow_upward`, `arrow_downward`, `reply`; Settings group icon `forum`. Upvoted = `--accent` on `--accent-soft`; downvoted = `--danger` on `--bg-danger`.
- Transloco keys in all four dictionaries (`frontend/public/i18n/{en,de,fr,es}.json`; fr *vous*, es *tú*, de as the dictionary already addresses the reader).
- No real credentials anywhere; fixtures use `lemmy.example`, `feddit.example`, `origin.example` and the JWT `test-jwt-not-a-real-token`.
- Clean Code rules of `CLAUDE.md`; `composer check && composer md` clean on every touched `src` file (`bin/console cache:warmup` before `composer stan`); `npm run check` green.

## Review Focus

1. **Credential containment.** The password is sent once to `/api/v3/user/login` and never stored, logged or hinted; the JWT goes only to the account's own instance — the anonymous `ap_id` lookup on the feed instance carries no `Authorization`. → Task 3 `testALemmyConnectSealsTheTokenNotThePassword` (opened credential is `test-jwt-not-a-real-token`, hint `''`); Task 4 `testAFederatedCopyIsLookedUpWithoutTheToken`.
2. **Federated copies.** An entry from `feddit.example/post/7` voted as a `lemmy.example` account must act on the post `resolve_object` finds for the origin `ap_id`, not on id 7. → Task 4 `testAFederatedCopyResolvesItsOriginOnTheHomeInstance`; Task 6 `testAVoteOnAFederatedCopyActsOnTheResolvedPost`.
3. **Lemmy must not reach feed-shaped code.** No Home feed on connect, never due for sync, 404 for import / search by account id, no `lemmy` network exclusion or saved-search inclusion, no link post. → Task 2 tests; Task 3 `testConnectingLemmyCreatesNoFeed`.
4. **Per-account thread cache.** The authenticated thread (with `my_vote`) is cached under `account:<id>` and never served to the public scope or another account, and the anonymous thread keeps its shared scope. → Task 8 `testAnAccountReadsItsOwnCacheScope` and `testWithoutAnAccountTheScopeStaysShared`.
5. **Vote arithmetic and revert.** Pressing the active arrow clears the vote; flipping moves the score by 2; a failure restores *both* `myVote` and `score`; a vote while one is on the wire is dropped. → Task 12 `nextVote` / `steppedScore` table test and `EntriesStore` `restoresTheVoteAndScoreOnFailure`; Task 13 `CommentsService` `revertsAFailedCommentVote`.
