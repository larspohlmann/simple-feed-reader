# #1109 Card-Image Recovery — Review Fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the 10 findings (F1–F10) of the independent code review of `feature/1109-card-image-recovery`, so the background image verify never makes a card worse than `develop` does.

**Architecture:** `EntryImage` becomes an explicit state machine: `image_verify_attempts IS NOT NULL` is the one pending marker (indexed), `image_checked_at` only ever means "when this instance judged the image", and a dropped image keeps its `checkedAt` as a tombstone. The fetcher tells "the host refused us / we cannot judge" (`FaviconRejectedException`) apart from "unreachable", and the verifier keeps the image in the first case. The feed-item selector goes back to strict source precedence; the http→https upgrade plus the verify does the recovery.

**Tech Stack:** PHP 8.4, Symfony 7.4, Doctrine ORM 3 / Migrations, PHPUnit 12, MySQL 8.4 (Docker) + SQLite (native).

**Spec:** GitHub issue #1109 (`gh issue view 1109`); original plan `docs/superpowers/plans/2026-09-21-1109-card-image-recovery.md`; review findings + verification in `.superpowers/sdd/2026-09-21-1109-card-image-recovery/progress.md` (block "INDEPENDENT /code-review").

**The rule (exact):**

| Fetch result | Exception | Verifier |
|---|---|---|
| HTTP `404` or `410` | `FaviconUnavailableException` | retry, then drop |
| any other `4xx` (401, 403, 429, 451 …) | `FaviconRejectedException` | keep + stamp checked |
| `5xx`, transport error, SSRF guard refusal, too many redirects, empty body | `FaviconUnavailableException` | retry, then drop |
| content type `image/*` outside the allow-list (avif, svg+xml, jpg …) | `FaviconRejectedException` | keep + stamp checked |
| any non-`image/*` content type (a soft-404 HTML page), or none | `FaviconUnavailableException` | retry, then drop |
| body over `MAX_BYTES`, or wire cap (`ResponseTooLargeException`, also when it arrives as the `getPrevious()` of a transport exception) | `FaviconRejectedException` | keep + stamp checked |
| bytes GD cannot decode | — | retry, then drop (unchanged) |

The SSRF boundary is untouched: same `UrlGuard` per hop, same IP pinning, same caps, SVG bytes are still never returned to any caller. `FaviconRejectedException` IS-A `FaviconUnavailableException`, so `CatalogFaviconWarmer` and `DigestImageEmbedder` behave exactly as before.

    public static function orNull(?string $url): ?string

        return self::withinColumn(self::secure($url ?? ''));

    public static function orNullUpgrading(?string $url): ?string
    {
        return self::withinColumn(self::secure($url ?? '') ?? self::upgraded($url ?? ''));
    }

    private static function secure(string $url): ?string
    {
        $rest = self::withoutPrefix($url, 'https://') ?? self::withoutPrefix($url, '//');

        return $rest === null ? null : 'https://' . $rest;
    }

    private static function upgraded(string $url): ?string
    {
        $rest = self::withoutPrefix($url, 'http://');

        return $rest === null ? null : 'https://' . $rest;
    }

    private static function withoutPrefix(string $url, string $prefix): ?string
    {
        return strncasecmp($url, $prefix, \strlen($prefix)) === 0 ? substr($url, \strlen($prefix)) : null;
    }

    {
        return $url === null || mb_strlen($url) > self::MAX_LENGTH ? null : $url;
