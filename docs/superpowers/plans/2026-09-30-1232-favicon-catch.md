# Drop Unreachable Catch Types in FaviconFetcher (#1232) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Base:** origin/develop at `0d9b14c80` (`0d9b14c806215e11fc8196adcd7b139a04e675ef`). symfony/http-client `v7.4.14` (composer.lock at that SHA).

**Goal:** `FaviconFetcher::download()` catches only what its try block can throw: `FetchException | TransportExceptionInterface`. The three HTTP-status exception interfaces leave the catch, their `@throws` tags and their imports. No behaviour changes. One PR, `Closes #1232`.

**Architecture:** One file, `backend/src/Service/Image/FaviconFetcher/FaviconFetcher.php`. The existing `FaviconFetcherTest` already pins both remaining catch members; `composer infection:diff` (the `Catch_` mutator on the touched catch line) proves it.

**Branch:** `chore/1232-favicon-catch` off origin/develop.

## Decisions

- **D-1: the file moved.** The issue names `backend/src/Service/Favicon/FaviconFetcher.php` "around line 71"; at `0d9b14c80` it is `backend/src/Service/Image/FaviconFetcher/FaviconFetcher.php:61-67`, and its test is `backend/tests/Service/Image/FaviconFetcher/FaviconFetcherTest.php`. The issue's gate `php bin/phpunit tests/Service/Favicon` becomes `php bin/phpunit tests/Service/Image/FaviconFetcher`.
- **D-2: the issue's reasoning holds, checked call by call.** The try block runs `fetchFollowingRedirects()` (`FaviconFetcher.php:60`). These are the HttpClient calls it reaches:
  - `getStatusCode()` (`:112`, and `FailoverRequestSender.php:83,128`): only `TransportExceptionInterface`. `TransportResponseTrait.php:51-58` returns `$this->info['http_code']` after `initialize()`, with no status check.
  - `getHeaders(false)` (`:166`, and `ResponseHeader::first()` at `Fetch/Support/ResponseHeader.php:15`): `TransportResponseTrait.php:66` calls `checkStatusCode()` only `if ($throw)`. `ResponseHeader::first()` also catches `ExceptionInterface` itself.
  - `getContent()` (`:168`, `$throw` defaults to true): `CommonResponseTrait.php:46-47` runs `checkStatusCode()`, which throws `ServerException` at 500 or above, `ClientException` at 400 or above, and `RedirectionException` at 300 or above (`CommonResponseTrait.php:161-176`). This is the only call that can throw the three. It runs only after `assertOk($status)` (`:164`), and `assertOk()` returns only on `if (200 === $status) {` (`:173`). Every other status throws a `Favicon*Exception`, which the catch does not handle. `checkStatusCode()` reads `getInfo('http_code')`, the same field `getStatusCode()` returned, so it sees 200 and passes. In dev, `TraceableResponse::getContent()` repeats the check with `$this->response->getStatusCode()` (`TraceableResponse.php:99-101`), which is still 200. No retry or async decorator wraps `http_client` (no `retry_failed` in `backend/config`).
  - `toArray()` is not called anywhere in the file.
  - A body-stream failure reaches the caller as a `TransportException`, not one of the three: `ErrorChunk.php:46` throws `new TransportException($this->errorMessage, 0, $this->error)`. That is why no MockHttpClient test can reach the three.

  Nothing else in the try block can throw one of the three, so no member of the three stays.
- **D-3: `getContent()` keeps its default flag.** Writing `getContent(false)` would state the invariant in code. It would also add an equivalent `FalseValue` mutant on the touched line, which needs its own `infection.json5` ignore (the `HtmlPageFetcher::content` precedent). The `assertOk()` guard two lines above already makes the default flag harmless.
- **D-4: the `@throws` tags go with the catch.** `fetchFollowingRedirects()` (`:103-105`) and `readSuccessfulResponse()` (`:158-160`) declare the three. Keeping those tags after the catch drops them would say `download()` leaks them. No PHPStan rule, test, config or doc outside this file names the three for FaviconFetcher (`git grep` in Task 1, Step 1). PhpStorm may raise "Unhandled exception" on `getContent()` for them, because it reads the contract's `@throws` whatever the flag. That inspection is a weak warning, which is advisory, the same as at the repo's other `getContent()` callers.
- **D-5: no new test.** The kept members are already pinned. If `FetchException` is dropped, `testPropagatesTheSsrfGuardAsAnUnavailableIconNotARejectedOne` fails, because `SsrfBlockedException extends FetchException` escapes from `UrlGuard::assertSafe()`. If `TransportExceptionInterface` is dropped, `testAnUnavailableFetchCarriesNoErrorCode` and `testARejectedFetchCarriesNoErrorCode` fail. Infection's `Catch_` mutator on the changed catch line produces exactly those two mutants and must kill both.
